# 2.0.n 工程经验总结：从 v2.0.n 的失败与成功中得到的方法论

## 结论先行

以下为 v2.0.n 全系列提炼的全部工程经验，后文逐条展开论证。

### 核心结论

**本质关系**：迷宫局部行为的最小语义原子是 `toward > away > wall`；success、timeout、visit、stuck、explore、recovery 等均为覆盖真实训练分布的上下文修正，不可替代这三个原语。

**一句话总结**：先把问题的本质定义到最小，再围绕这个本质构造数据、设计压力、输出 debug，最后才训练模型。

### 全部工程经验清单

1. **先把目标定义清楚**
   - 很多训练失败并非模型不够大、epoch 不够多、reward 不够强，而是目标定义不清楚
   - 不要一开始就用复杂标签解释问题；先找到最小语义原子，再用复杂数据分布覆盖这些原子会出现的上下文

2. **不要用笼统表达掩盖问题本质**
   - `success > timeout`、`safe > wall` 等全局标签无法推出局部动作价值
   - 模型易学到伪相关（如 `low visit = good`、`away 很好`），导致 pure argmax 中 away choice 偏高、stuck timeout
   - 全局标签负责覆盖行为分布；局部 pair 负责表达本质关系；不要指望全局 outcome 自动推出局部动作价值

3. **全局与局部要分工明确**
   - 全局轨迹：让 RM 看到训练中真实会出现的完整行为分布（绕路成功、高 visit、撞墙恢复、探索未成功、stuck timeout 等），允许探索与恢复，防止上下文变量被误学成绝对坏信号
   - 局部 pair：在同一状态、同一 visit map、同一上下文中做反事实比较（`toward > away`、`non-wall > wall`、`escape > continue_loop`）
   - 全局轨迹负责分布覆盖；局部片段负责语义约束；二者不能互相替代

4. **用 primitive pressure 让调参从"赛博炼丹"变成可解释工程**
   - primitive pressure 是语义诊断向量，回答 toward / away / wall / visit 分别被数据往哪个方向推
   - 它是方向诊断，不是 reward 输出的线性预测器；模型结构、tanh 饱和、样本可分性都会影响最终 reward
   - 调参不能只看 loss，也不能只看 reward probe；最好同时看数据压力、训练结果和 rollout 失败类型

5. **Debug 输出必须工程化**
   - success rate、loss、accuracy 只能告诉我们"效果不好"，不能告诉我们"为什么不好"
   - debug 不应只是记录结果，应直接支持下一步决策
   - 好的 debug 应回答：问题在哪里？哪类样本 / pair 导致？是数据、margin、模型还是策略问题？

6. **用 RM 轨迹偏好缓解稀疏奖励是有效的，但不是终点**
   - BFS 专家轨迹 + BTL preference + 局部 pair 可将 RM 从轨迹排序器推进到局部 reward model
   - 未来迷宫更复杂时，专家轨迹不可得、最优不唯一、探索有价值、动作有概率
   - 后续需扩展：weak preference → 概率偏好 → failure mining → 在线 RM → uncertainty-aware reward → 多目标 reward

7. **遇到 RL / RM 失败时的标准排查顺序**
   - 第一步：确认目标能否被更小的原语表达，有没有把 outcome、过程、上下文混在一起
   - 第二步：构造最小可验证任务——监督 BFS 先于 RL；监督下不能规划，不要期待 RL 下自己学会
   - 第三步：全局数据覆盖真实分布，局部数据表达因果关系
   - 第四步：固定上下文、只改变一个因素，做反事实比较
   - 第五步：让 debug 面向决策（toward-away 小调 progress、away 高查 wall bucket 正样本等）
   - 第六步：区分数据 / reward / 模型 / 策略问题（reward probe 正确但 policy 失败 → 问题在 policy 模型）

8. **本轮最重要的反思**
   - v2.0.n 的失败逐步剥离清楚：不是 reward 数字不够、不是 DQN epoch 不够、不是 RM accuracy 不够、不是 wall penalty 不够
   - 而是目标语义、数据分布、局部因果关系、模型规划能力需要分别处理
   - v2.0.9 后 RM 已学得相当合理，但 CNN 仍无法像 BFS 一样规划——瓶颈已从 RM 转向策略模型

## 1. 最大收获：先把目标定义清楚

v2.0.n 这一轮最大的工程收获是：很多训练失败并不是模型不够大、epoch 不够多、reward 不够强，而是目标定义不清楚。

最开始，我们试图用更笼统的表达描述迷宫中的好坏行为，例如：

```text
success > timeout > wall
BFS > long success > timeout
no repeat > repeat
clean timeout > stuck timeout
visit2 recovery > visit3 loop
```

这些定义并非完全错误，但它们混合了太多层次：全局 outcome、局部动作、访问历史、路径长度、探索程度、墙、循环、恢复行为都被混在一起。模型得到的训练信号就会变得混杂。

后来 v2.0.9 的成功说明，问题的本质其实更简单：

```text
toward
away
wall
```

其中：

```text
toward = 朝 BFS 目标方向推进
away   = 偏离目标但仍可恢复
wall   = 明确无效动作
```

这三个动作原语才是迷宫局部行为判断的核心。

visit、loop、success、timeout、wall recovery、high visit recovery、explore timeout 等全局轨迹设计不是问题的本质，而是为了覆盖 QCNN / policy 在训练中可能产生的行为分布。它们的作用是帮助模型在更多上下文中学习这三个基本关系，而不是替代这三个基本关系。

工程经验：

```text
不要一开始就用复杂标签解释问题。
先找到问题最小的语义原子。
再用复杂数据分布覆盖这些原子会出现的上下文。
```

在本项目中，最小语义原子就是：

[
toward \succ away \succ wall
]

其它 visit、stuck、explore、recovery 都是围绕这个核心关系展开的上下文修正。

## 2. 不要用更笼统的表达掩盖问题本质

早期多次失败都来自一个共同问题：用笼统概念训练模型，希望模型自己拆出细节。

例如：

```text
success > timeout
```

看似合理，但它并不能告诉模型：

```text
success 中哪些 step 是好的？
timeout 中哪些 step 是坏的？
timeout 中有没有 toward step？
success 中有没有 wall 或 high visit？
```

如果 success 大多是 low visit，timeout 大多是 high visit，模型就可能学到：

```text
low visit = good
high visit = bad
```

但这不是本质。因为 high visit 后仍然可能 recovery success，visit2 可能是死胡同回撤，visit3+ 也可能仍然有 escape action。

同样，safe > wall 也有问题。safe 可能包含 toward，也可能包含 away。如果正样本里 away 占比过高，模型会被间接训练成：

```text
away 很好
```

这会导致 pure argmax 中 away choice 偏高，最终进入 stuck timeout。

工程经验：

```text
全局标签负责覆盖行为分布；
局部 pair 负责表达本质关系；
不要指望全局 outcome 自动推出局部动作价值。
```

## 3. 全局与局部要分工明确

v2.0.n 中一个重要转折是把全局轨迹和局部片段分开。

全局轨迹的作用不是精确定义每一步 reward，而是让 RM 看到智能体在训练中可能产生的完整行为分布：

```text
成功但绕路
成功但高 visit
成功但撞墙后恢复
探索但未成功
小范围 stuck
严重 wall timeout
```

这些全局轨迹尤其重要，因为我们观察到 QCNN 初期探索时会出现各种不理想行为。如果全局轨迹过于干净，模型会以为只有 BFS 是好行为，结果一旦 QCNN 偏离 BFS，就无法恢复。

因此，全局轨迹的工程目标是：

```text
允许探索；
允许恢复；
允许少量错误；
覆盖训练中真实会出现的失败形态；
防止模型把某个上下文变量误学成绝对坏信号。
```

局部 pair 的作用则不同。局部 pair 应该直接表达本质关系：

```text
toward > away
non-wall > wall
escape_from_stuck > continue_loop
same_direction_low_visit > same_direction_high_visit
```

局部 pair 不是为了模拟完整 episode，而是为了在同一状态、同一 visit map、同一上下文中进行反事实比较。

工程经验：

```text
全局轨迹负责分布覆盖；
局部片段负责语义约束；
二者不能互相替代。
```

## 4. 梯度压力让调参从"赛博炼丹"变成可解释工程

本项目中一个重要经验是定义了 primitive pressure。

它不是实际梯度范数，也不是单个 margin 的量纲。它是一个语义诊断向量，用来回答：

```text
当前训练数据整体在把 toward 往哪里推？
在把 away 往哪里推？
在把 wall 往哪里推？
在把 visit 往哪里推？
```

我们使用类似下面的形式计算：

[
Pressure_k=
\sum_b
\pi_b
\cdot
q_b
\cdot
E[m_b]
\cdot
\Delta \phi_{b,k}
]

其中：

```text
π_b      = bucket 在总 pair 中的占比
q_b      = valid rate
E[m_b]   = bucket 的平均 margin
Δφ_b,k   = 正负样本在某个 primitive 上的平均差异
```

这个量化帮助我们避免纯粹靠感觉调参。

例如：

```text
toward-away 不够 → 增加 progress pair / margin；
away 被抬高 → 检查 wall bucket 中 away positive 占比；
visit 压过 wall → 降低 visit 极端 pair，增加 high visit success；
wall reward 已经很低但 pressure 不足 → 不盲目加 wall，而结合 reward probe 判断。
```

虽然 v2.0.9 中出现过一个有趣现象：wall 的负 primitive pressure 不算特别大，但训练后的 wall reward 惩罚非常强。这说明 primitive pressure 不是 reward 输出的线性预测器。模型结构、tanh 饱和、样本可分性、局部特征强度都会影响最终 reward。因此，primitive pressure 应该作为"方向诊断"，而不是单独作为调参裁判。

工程经验：

```text
调参不能只看 loss；
也不能只看 reward probe；
最好同时看数据压力、训练结果和 rollout 失败类型。
```

## 5. Debug 输出必须工程化

早期版本中 debug 输出比较粗糙，经常只能看到 success rate、loss、accuracy、wall rate。问题是，这些指标只能告诉我们"效果不好"，不能告诉我们"为什么不好"。

后期版本逐步形成了更有用的 debug 体系：

```text
Sample Profile Distribution
Primitive Distribution by Sample Profile
Local Bucket Context Distribution
Bucket Primitive Pressure Contribution
Observed Primitive Pressure
RM Primitive Reward Score Report
Contextual Probe
Greedy Difficulty Breakdown
Stuck Timeout Analysis
Failure Tail Action Rank Report
```

这些 debug 指标能帮助定位具体问题：

```text
toward-away gap 小       → progress 不够；
away p50 太高            → away 被 wall bucket 抬高；
wall p90 / pct_pos_one 高 → wall 尾部异常；
visit_mean > 0           → visit 校准不足；
all_actions_saturated 高  → 动作区分饱和；
hard success 掉得多       → 模型规划能力不足；
stuck tail 中 escape 可用但没选 → escape reward 不够；
```

工程经验：

```text
debug 不应该只是记录结果；
debug 应该直接支持下一步决策。
```

一个好的 debug 表应该回答：

```text
问题在哪里？
是哪类样本导致的？
是哪类 pair 导致的？
是数据问题、margin 问题、模型问题，还是策略问题？
```

## 6. 用 RM 轨迹偏好缓解稀疏奖励是有效的，但不是终点

本轮项目证明，使用 RM 解决稀疏奖励是可行的。迷宫任务中 BFS 专家轨迹容易获取，因此我们可以非常准确地定义：

```text
什么是好轨迹；
什么是坏轨迹；
什么是局部更好的分支；
什么是恢复；
什么是 stuck；
什么是 wall。
```

这比直接手写 reward 更灵活。尤其是 BTL preference 允许我们只定义相对好坏，而不必一开始就给每个动作写死 reward 数值。

更重要的是，局部轨迹 pair 可以把全局偏好拆成每一步的 reward 语义：

```text
同一状态下 toward > away；
同一状态下 non-wall > wall；
高 visit loop 中 escape > continue_loop。
```

这让 RM 不只是轨迹排序器，而逐渐接近局部 reward model。

但是，这条路线不能浅尝辄止。未来迷宫会变得更复杂、更概率化、更不可观测。一旦进入概率迷宫或二进制漏洞挖掘，BFS 专家轨迹未必容易获得，什么是"好轨迹"也不再总是确定的。

未来会遇到的问题包括：

```text
专家轨迹不可得；
最优轨迹不唯一；
短期 away 可能是长期最优；
探索本身具有价值；
动作结果有概率；
状态空间无法完全枚举；
奖励更稀疏；
失败原因更多样。
```

因此，RM 路线后续还需要继续发展：

```text
1. 从 BFS expert preference 扩展到 weak preference；
2. 从确定轨迹偏好扩展到概率偏好；
3. 从人工构造 pair 扩展到 failure mining；
4. 从离线 RM 扩展到在线更新 RM；
5. 从固定 reward 扩展到 uncertainty-aware reward；
6. 从单目标 reward 扩展到 exploration / coverage / risk 的多目标 reward。
```

## 7. 工程上遇到类似问题时，一般怎么做

结合更广泛的工程经验，遇到强化学习或奖励建模失败时，通常不应该直接加模型规模或训练时间，而应按以下顺序定位。

### 第一步：确认目标是否可定义

先问：

```text
我们到底希望模型学什么？
这个目标能不能被更小的原语表达？
有没有把 outcome、过程、上下文混在一起？
```

在本项目中，真正目标不是 "success > timeout" ，而是：

```text
toward > away > wall
```

success / timeout 只是这些局部动作长期累积后的结果。

### 第二步：构造最小可验证任务

不要直接在完整 RL 中调参。应先做监督任务或局部反事实任务。

在本项目中，后续 1.x.y 就是这个思路：先验证模型能不能学 BFS，再讨论 DQN。

通用经验：

```text
如果模型在监督 BFS 下都不能规划，不要期待它在 RL 下自己学会规划。
```

### 第三步：把全局数据和局部数据分开

全局数据负责覆盖真实分布，局部数据负责表达因果关系。

类似做法在很多工程中都存在：

```text
自动驾驶中，全局轨迹覆盖各种路况，局部 pair 训练避障、让行、跟车；
机器人中，episode 成功失败覆盖任务，局部 transition 训练 grasp / avoid collision；
推荐系统中，全局 session 表示长期满意度，局部 pair 表示 item preference；
漏洞挖掘中，全局执行路径表示覆盖结果，局部 mutation pair 表示哪类输入变异更有价值。
```

### 第四步：做反事实比较

如果只比较不同上下文的样本，模型容易学到伪相关。更好的方法是固定上下文，只改变一个因素。

本项目中的例子：

```text
same state, same visit map:
  toward action > away action

same state:
  non-wall action > wall action

same high-visit loop:
  escape action > continue loop
```

这比笼统比较 success 和 timeout 更能告诉模型因果关系。

### 第五步：让 debug 面向决策

工程上最差的 debug 是只输出很多数字，但不知道怎么用。好的 debug 应该直接告诉你：

```text
如果 toward-away 小，就调 progress；
如果 away 高，就检查 wall bucket 正样本；
如果 visit 高，就调 visit band；
如果 wall 已经 -1，就不要继续加 wall；
如果 saturated 高，就增加 hard negative 或降低饱和；
如果 hard maze 差，就检查模型规划能力。
```

### 第六步：区分数据问题、reward 问题和模型问题

本项目最后的重要结论是：RM 已经学得相当合理，但 CNN 仍然无法像 BFS 一样规划。这个结论很重要，因为它阻止我们继续在 RM 上无意义地调参。

通用经验：

```text
如果 reward probe 正确，但 policy 失败，问题可能在 policy 模型；
如果 supervised planner 都失败，问题在模型表达能力；
如果 supervised planner 成功但 RL 失败，问题在探索或 credit assignment；
如果 local probe 错，问题在 reward 数据或 pair 设计。
```

## 8. 本轮最重要的反思

v2.0.n 的失败不是浪费，而是逐步把问题剥离清楚：

```text
不是 reward 数字不够；
不是 DQN epoch 不够；
不是 RM accuracy 不够；
不是 wall penalty 不够；
而是目标语义、数据分布、局部因果关系、模型规划能力需要分别处理。
```

最终经验可以总结为一句话：

```text
先把问题的本质定义到最小，再围绕这个本质构造数据、设计压力、输出 debug，最后才训练模型。
```

在本项目中，这个本质就是：

[
toward \succ away \succ wall
]

visit、stuck、explore、recovery 都是为了让模型在真实训练分布中仍然稳定保持这个关系。

这也是后续项目继续推进时最应该保留的工程思想。
