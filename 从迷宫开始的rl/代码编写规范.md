# 代码编写规范：按版本目录冻结公共模块

## 1. 核心原则

本项目后续不再采用“整个 feature 下一个全局 common”的结构。

正确原则是：

```text
feature_maze 下每一个大版本目录拥有自己独立的 common 模块。
```

也就是说，每一代版本内部可以复用公共代码，但不同代之间不共享同一套公共模块。

这样做的原因是：

```text
1. 每一代实验目标不同，公共基础设施也会不同；
2. v1.x 是 BFS 监督学习，不需要 v2.0 的 RM trajectory pair 体系；
3. v2.0 是 reward model + Q model，不应被 v2.1 的概率迷宫环境污染；
4. v2.1 以后会引入复杂化、概率化、探索化环境，maze_env 语义会变化；
5. 独立 common 可以冻结每一代的基础组件，避免代理无意改动跨代代码；
6. 每一代目录都可以独立归档、复现和审查。
```

最重要的目标是：

```text
同一代内部稳定复用；
不同代之间版本隔离；
代理只能修改当前代目录；
不允许跨代偷偷 import 或重写公共模块。
```

## 3. 为什么不使用全局 common

全局 common 看似更“标准”，但不适合当前项目。

原因是本项目处于研究探索阶段，不同代的环境定义会变化：

```text
v1.x:
  重点是 BFS 监督学习。
  需要的是 BFS label、distance field、policy classifier、rollout success。

v2.0:
  重点是 reward model 和 Q model。
  需要 trajectory、segment、BTL pair、primitive pressure、RM probe。

v2.1:
  重点是复杂化和概率化迷宫。
  maze_env 本身会变，step 不再完全确定。
```

如果强行使用全局 common，会导致：

```text
1. v2.1 修改 maze_env 时可能破坏 v2.0；
2. v2.0 的 trajectory pair 数据结构会污染 v1.x；
3. v1.x 的 BFS 监督任务会被迫依赖 RM 概念；
4. 代理可能为了新实验修改全局模块，导致旧实验不可复现。
```

所以本项目采用：

```text
version-local common
```

即：

```text
每个大版本有自己的 common；
跨大版本不共享 common；
需要迁移的代码通过复制 + 审查，而不是直接 import。
```

## 4. 跨版本复用规则

不同大版本之间可以借鉴代码，但不能直接依赖。

禁止：

```python
from feature_maze.v2_0_reward_model.common.bfs import bfs_distances
```

在 `v2_1_complex_maze` 中这样跨代 import 是禁止的。

正确做法：

```text
1. 如果 v2.1 需要 v2.0 的某个工具函数；
2. 先复制到 v2_1_complex_maze/common/；
3. 根据 v2.1 的环境语义审查是否需要修改；
4. 在 README 或 migration note 中记录来源。
```

建议保留迁移记录：

```text
v2_1_complex_maze/MIGRATION.md
```

内容例如：

```text
Copied bfs.py from v2_0_reward_model/common on 2026-xx-xx.
Modified reachable mask to support stochastic blocked cells.
```

## 5. 同一代内部的公共模块冻结规则

在同一个大版本内部，`common/` 是稳定层。

例如 `v2_0_reward_model/common/` 中的：

```text
maze_env.py
bfs.py
state_encoder.py
reward_models.py
rollout.py
probes.py
reports.py
```

一旦稳定，就不应在每个实验中重复改写。

普通实验只能修改：

```text
experiments/
configs/
```

默认不允许修改：

```text
common/
```

如果必须修改 common，必须先说明：

```text
1. 为什么实验脚本不能解决；
2. 修改哪个 common 文件；
3. 修改哪个函数 / 类；
4. 是否影响同代已有实验；
5. 是否需要保留旧函数；
6. 如何测试。
```

## 6. 每代 common 的职责划分

### 6.1 v1_x_bfs_models/common

只服务 BFS 监督学习。

应包含：

```text
maze_env.py          确定性迷宫环境
bfs.py               BFS distance / shortest path / labels
state_encoder.py     BFS 模型输入编码
bfs_dataset.py       BFS supervised dataset
models.py            CNN / U-Net / ResNet / VIN / GNN / Transformer
rollout.py           supervised policy rollout
metrics.py           action acc / distance MAE / success / shortest path rate
reports.py           表格和 json 报告
plotting.py          训练曲线和 rollout gif
io_utils.py          保存加载工具
cli_utils.py         preset / seed / tqdm / run_name
```

不应包含：

```text
Reward Model
BTL preference pair
DQN replay buffer
Q learning
primitive pressure
```

### 6.2 v2_0_reward_model/common

只服务 v2.0 的 RM + Q model。

应包含：

```text
maze_env.py             确定性迷宫环境
bfs.py                  BFS 工具
state_encoder.py        RM/Q 输入编码
trajectory.py           Trajectory / Segment 数据结构
preference_pairs.py     Pair 数据结构与 validator
reward_models.py        RM backbone
q_models.py             Q model backbone
rm_losses.py            BTL-margin loss
rollout.py              RM greedy / Q rollout
probes.py               primitive/contextual/greedy/stuck probes
reports.py              profile / pressure / reward report
plotting.py             curves / gif
io_utils.py             json / checkpoint / metadata
cli_utils.py            preset / tqdm / seed / device
```

### 6.3 v2_1_complex_maze/common

服务复杂化、概率化迷宫。

应包含：

```text
maze_env.py             基础复杂迷宫
stochastic_maze_env.py  概率墙 / 随机转移
bfs.py                  确定性参考 BFS 或期望 BFS
state_encoder.py        局部可观测 / belief state 编码
exploration_metrics.py  coverage / novelty / information gain
reward_models.py        可选 RM
q_models.py             DQN / planning model
rollout.py              stochastic rollout
probes.py               exploration probe / risk probe
reports.py              概率任务报告
```

## 7. 实验脚本职责

实验脚本不应该重复实现公共模块。

实验脚本只负责：

```text
1. 加载 config；
2. 选择 common 中已有模型；
3. 定义本实验的数据配方；
4. 定义本实验的训练流程；
5. 调用 common 的 probe 和 report；
6. 保存输出。
```

实验脚本可以定义：

```text
sample profile
pair bucket recipe
loss 权重组合
模型选择
训练 schedule
评估组合
```

实验脚本不应该定义：

```text
BFS 算法
maze step
RewardModel 网络类
QModel 网络类
print_table
rollout 基础函数
json 保存函数
```

## 8. 模型结构保护规则

所有模型结构必须位于当前代的 `common/models.py`、`common/reward_models.py` 或 `common/q_models.py` 中。

禁止在实验脚本中临时定义模型，除非该版本明确就是“新增模型实验”。

如果新增模型，必须：

```text
1. 放入当前代 common；
2. 写清楚 model name；
3. 在 config 中选择；
4. 在终端 Model Summary 中打印；
5. 在 run_metadata.json 中保存；
6. 在 README 中记录。
```

特别注意：

```text
不得偷偷把 CNNRewardModel 改成 LinearMLPRewardModel。
不得在实验脚本里覆盖同名类。
不得让不同版本同名模型结构不同却不记录。
```

## 9. 配置文件规范

每个大版本目录下都有自己的 configs。

例如：

```text
v2_0_reward_model/configs/default.yaml
v2_0_reward_model/configs/large.yaml
```

配置必须完整描述本实验：

```yaml
version: v2.0.10_model_swap
seed: 42

maze:
  grid_size: 8
  max_steps: 64

state_encoder:
  channels:
    - wall
    - agent
    - goal
    - visit_map

rm_model:
  name: TransitionCNNRewardModel
  output_activation: tanh

dataset:
  rm_mazes: 400
  pair_recipe: stuck_away_rebalanced

training:
  epochs: 8
  batch_size: 64
  lr: 0.0003

probe:
  greedy_mazes: 100
  debug_mazes: 50
```

运行时必须保存：

```text
resolved_config.yaml
```

```text

```

```text

run_metadata.json
training_history.json
evaluation_summary.json
```

具体实验再增加自己的报告。

## 11. README 规范

每个大版本目录必须有 README。

例如：

```text
v2_0_reward_model/README.md
```

内容包括：

```text
1. 本代目标；
2. 本代 common 模块说明；
3. 本代实验列表；
4. 不允许修改的稳定模块；
5. 当前推荐入口脚本；
6. quick / default / large 命令；
7. 已知问题；
8. 下一步计划。
```

这样代理和人都能先读 README，再决定改哪里。

## 12. 代理协作提示词规范

之后让代理写代码时，应明确限定工作范围。

推荐模板：

```text
请在 feature_maze/v2_0_reward_model/ 下新增实验版本。
禁止修改 feature_maze/v2_0_reward_model/common/。
必须复用当前代 common 中的 maze_env.py、bfs.py、state_encoder.py、reward_models.py、rollout.py、probes.py、reports.py。
只允许新增 / 修改 experiments/ 和 configs/。
如果你认为必须修改 common，请先停止并说明理由，不要直接改。
```

如果允许修改 common，应写：

```text
本次允许修改 feature_maze/v2_0_reward_model/common/reward_models.py。
只允许新增一个模型类，不允许改已有模型类。
必须保持旧 checkpoint 可加载。
```

## 13. 同名文件与缓存规范

不要覆盖旧实验脚本。

如果是同一实验修正版：

```text
train_2_0_10_model_swap.py
train_2_0_10_model_swap(1).py
train_2_0_10_model_swap(2).py
```

或者更推荐：

```text
train_2_0_10_model_swap_v1.py
train_2_0_10_model_swap_v2.py
```

用户已经明确说明：同名文件可能因为底层缓存导致看不到修改。

因此原则是：

```text
修改后必须改名；
不要发送同名文件；
输出文件 VERSION 也要同步变化。
```

## 14. Protocol Compliance Audit

每个实验启动时必须做协议审计。

至少检查：

```text
1. 当前脚本位于正确版本目录；
2. 是否错误 import 了其它代 common；
3. VERSION 是否匹配脚本；
4. model name 是否来自当前代 common；
5. 是否启用了禁止的阶段；
6. output_dir 是否正确；
7. config 是否保存；
8. required reports 是否注册；
9. common 是否被本次实验修改。
```

终端输出：

```text
[Protocol Compliance Audit]
status: PASS
```

如果失败，必须中止或明确 warning。

---

## 15. 最终原则

本项目代码组织的最终原则是：

```text
每一代版本自带自己的 common；
同代实验复用同代 common；
跨代代码不直接 import；
公共模块默认冻结；
实验脚本只表达变化；
所有变化必须 config 化；
所有模型结构必须显式命名；
所有输出必须可追踪；
所有代理修改必须限定范围。
```

这样项目才能避免“版本越多，基础代码越混乱”的问题，也能保证每一次实验失败都能被准确归因。
