# 工程经验总结：编写原则

## 结论先行

以下为本文档规定的全部编写原则，后文逐条展开说明。

### 核心结论

**文档目的**：工程经验文档的价值在于提炼可迁移的方法论，不在于复述每个版本的实现细节或 changelog。

**一句话总结**：写工程经验时，先回答"学到了什么通用方法"，再按需引用具体版本作为例证；不要反过来从版本细节堆砌成文。

### 全部编写原则清单

1. **不深陷版本细节**
   - 不逐版本复述"改了什么参数、加了什么函数"
   - 综合整个系列（如 v2.0.n）的进步，提炼跨版本稳定的工程反思

2. **方法论优先于 changelog**
   - 重点不是"每个版本改了什么"，而是：如何发现问题、如何定义目标、如何组织数据、如何设计 debug、如何从失败中找到下一步方向

3. **面向决策而非面向记录**
   - 每一条经验应能回答：下次遇到类似问题时，第一步该做什么
   - 避免只描述现象（"效果不好"），要写清诊断路径与行动建议

4. **分层组织：结论先行，论证在后**
   - 文档开头列出核心结论与经验清单，读者可快速把握全貌
   - 正文再逐条展开论证、举例与反例

5. **区分层次，避免语义混杂**
   - 不把全局 outcome、局部动作、上下文变量写在同一层次里混谈
   - 写清楚"本质关系"与"分布覆盖"各自承担什么角色

6. **失败与成功同等重要**
   - 失败版本不是浪费，而是剥离问题边界的过程
   - 明确写出"排除了什么"（不是 epoch 不够、不是 penalty 不够），比只写成功做法更有参考价值

7. **与代码、debug 输出对齐**
   - 文档中的概念（如 primitive pressure、local pair）应与代码和 debug 报告中的术语一致
   - 读者应能从文档直接对应到仓库里的脚本与输出字段

8. **版本专属内容归入版本目录**
   - 通用编写原则放在项目根目录（本文档）
   - 某一阶段的完整工程经验（如 2.0.n）放在对应版本文件夹内，并同样遵循"结论先行"

---

## 1. 文档定位

工程经验总结不是实验日志，也不是 README 的重复。它的读者是未来的自己或协作者：在迷宫 RL、奖励建模、策略调试或迁移到更复杂任务（如二进制漏洞挖掘）时，需要快速 recall 哪些做法有效、哪些坑必须避开。

因此，文档应站在**系列整体**的高度写，而不是站在**单个 commit 或单个脚本**的高度写。

---

## 2. 不深陷每一个版本的实现细节

每个版本目录里已有完整代码与运行产物。工程经验文档不需要再抄一遍实现。

应当做的是：

```text
从多个版本的成败中，抽象出稳定的工程规律；
用少量典型版本（如 v2.0.0 baseline、v2.0.9 收敛点）作锚点；
其余版本作为"验证某条规律"的论据，而非正文主线。
```

反例（应避免）：

```text
v2.0.5 把 margin 从 0.3 改成 0.5；
v2.0.6 增加了 visit_count bucket；
v2.0.7 引入了 family margin……
```

这类流水账对方法论帮助有限，且会随代码迭代快速过时。

---

## 3. 重点：如何发现问题、定义目标、组织数据、设计 debug

一篇合格的工程经验总结，至少应覆盖以下五个问题：

```text
我们当初以为问题是什么？实际是什么？
目标有没有被拆到足够小的语义原子？
训练数据（全局轨迹 vs 局部 pair）各承担什么职责？
用了哪些 debug 指标定位失败，指标如何对应到下一步动作？
从失败中得到的下一版方向是什么？
```

强化学习项目中，很多问题表面是"模型不行"，实质是目标定义、数据分布或诊断链路的问题。文档要把这种**剥离过程**写清楚。

---

## 4. 结论先行的写法

长文档默认采用以下结构：

```text
1. 结论先行
   - 核心结论（1～2 句）
   - 全部经验 / 原则清单（编号列表，每条可独立阅读）
2. 分隔线
3. 正文
   - 按清单顺序逐条展开
   - 每条含：背景、反例、正例、可执行的工程经验块
```

这样读者可以先读清单做决策，再按需深入某一节。

---

## 5. 与阶段文档的关系

| 文档 | 位置 | 内容 |
|------|------|------|
| 编写原则（本文档） | `从迷宫开始的rl/工程经验总结.md` | 如何写工程经验、如何组织系列反思 |
| 阶段工程经验 | 如 `feature_maze/v2.0.n/2.0.n 工程经验总结.md` | 该阶段具体方法论与结论 |
| 项目背景与规划 | `项目背景以及规划.md` / `README.md` | 路线、版本规划、验收指标 |
| 代码编写规范 | `代码编写规范.md` | 代码风格与仓库约定 |

阶段文档必须遵循本文档的编写原则；本文档不替代阶段文档中的具体技术结论。

---

## 6. 从失败中找到下一步方向

编写经验总结时，_success_ 和 _failure_ 应成对出现：

```text
失败说明了什么假设不成立？
成功收窄了问题的哪一层（目标 / 数据 / RM / policy）？
若把经验迁移到新环境，哪一条仍成立，哪一条需要重写？
```

避免只写"最终 v2.0.9 成功了"，而不写中间版本如何逐步排除错误归因。

---

## 7. 修订与维护

- 新增阶段（如 2.1.x、1.x.y）时，在对应版本目录新增阶段总结，并更新 README 中的路线说明
- 若发现编写方式上的新共识（例如 debug 命名规范），补充到本文档的"结论先行"清单中
- 不在本文档中堆叠某一阶段的 primitive 定义或 pair 设计细节——那些属于阶段文档
