# 3.0.n 工程经验总结：从样本分布诊断到 TDA-QD MazeForge

## 0. 总结

3.0.n 的核心不是“不断设计更复杂的迷宫生成器”，而是一次从样本分布怀疑出发，逐步建立目标分布、验证器、候选池、调试链路和工程收官标准的过程。

最初的问题来自手绘迷宫测试：模型在生成器样本上可以训练，但面对人工手绘迷宫时泛化不足。因此 3.0.n 的第一性假设是：失败不一定来自模型结构，也可能来自训练样本分布与手绘测试分布之间的差异。

这个问题可以用机器学习工程中的 Distribution Shift — Distribution Shift — 分布偏移 来描述。它指训练数据分布和测试数据分布不一致，导致模型在训练环境中表现尚可，但在目标环境中失败。3.0.n 的工作就是围绕这个分布偏移，逐步回答几个问题：

1. 当前生成器分布是否足够接近手绘分布；
2. 如果不接近，应如何描述这种差异；
3. 描述指标能否直接变成生成控制指标；
4. 如果不能，是否需要更高层结构对象；
5. 严格构造是否值得继续推进；
6. 是否可以转向候选池、统一验证器和目标分布档案；
7. 最终样本集是否足够接近手绘目标分布，可以进入后续模型训练替换测试。

最终，3.0.n 收敛到 TDA-QD MazeForge — Terminal-Diameter Aligned Quality-Diversity MazeForge — 终端直径对齐的质量多样性迷宫工厂。它的意义不是某个单一算法技巧，而是将样本生成整理成一个完整数据工厂：

* 目标分布来自手绘样本；
* 候选样本由多个生成/变换机制提供；
* 最终分桶由可信 full extractor 决定；
* archive 根据目标分布接收样本；
* 输出包含可视化、CSV、报告和收官判断；
* 工程壳能够支持审查、复现和后续训练。

3.0.n 最重要的工程经验可以概括为一句话：

**不要先假设生成器应该长什么样；先定义目标域分布、稳定验证器，再让候选池和 archive 去逼近这个分布。**

---

## 1. 3.0.0：可解性不是目标分布

3.0.0 的主要任务不是立刻设计最终生成器，而是诊断现有生成器的分布偏置。

当时关注的两个代表性生成方向是：

**PBG — Path-Based Generator — 路径型生成器**
它倾向于先保证迷宫中存在一条可解路径，再围绕路径构造样本。它的优势是可解性强，但可能生成过于开放或结构单一的迷宫。

**RRG — Randomized / Recursive-style Generator — 随机/递归型生成器**
它更强调随机结构或递归式结构生成。它可能制造更多墙和局部障碍，但 fallback corridor 这类修复机制可能污染分布，使样本看起来复杂，实际却是固定风格的长通道。

3.0.0 的关键发现是：**solvable 只是入场条件，不是训练价值。**

一个迷宫生成器即使能够 100% 生成可解样本，也可能存在严重分布偏置。例如：

* 过度开放，导致模型见到大量局部自由区域；
* 过度走廊化，导致模型学到固定蛇形路径；
* fallback 样本占比较高，使 hard 样本的统计被修复逻辑主导；
* 平均指标看起来合理，但极端样本暴露出风格单一。

因此，3.0.0 形成的第一条经验是：

**样本生成工程的第一步不是增加数量，而是诊断分布。**

这也解释了为什么后续 3.0.n 一直强调可视化、极端样本检查、分布统计和 debug 报告。生成样本不是只要“能跑通”，而是要能说明它们覆盖了目标域中的关键结构。

## 2. 3.0.1：描述坐标不等于控制坐标

3.0.1 的核心尝试是 Path-First — Path-First — 路径优先生成，以及 7D / 多维指标控制。

Path-First 的基本思路是：先构造一条从起点到终点的主路径，再围绕这条路径补充墙、死胡同、岔路、绕路等结构。这个思路的前置假设是：如果主路径可控，那么其他复杂度指标也许可以通过局部编辑逐步控制。

这一阶段引入多维指标，是一种 Feature Engineering — Feature Engineering — 特征工程 / 指标工程。它的作用是把“手绘迷宫复杂”拆成可观察的维度，例如：

* 路径是否足够长；
* 墙是否足够多；
* 可达区域是否合理；
* 死胡同是否丰富；
* 岔路是否存在；
* 绕路程度是否足够；
* 主路径上是否有决策压力。

这些指标帮助我们从“感觉复杂”进入“可观测、可统计、可比较”的阶段。

但 3.0.1 的动态验证暴露了一个重要事实：**这些指标可以描述样本，但不能直接当作互相独立的控制旋钮。**

例如，拆墙会影响可达区域；可达区域变化会影响岔路；岔路变化会影响绕路；死胡同变化会影响端点数量；主路径长度也会影响可用空间。它们共享同一个底层网格图结构，所以不能简单地把 7D 指标拆成 7 个独立修改器。

这次失败不是负面失败，而是一次有效动态验证。它证明了一个关键假设不成立：

**描述坐标不等于控制坐标。**

这条经验在后续非常重要。未来如果某个任务提出多个指标，也不能默认这些指标可以被独立优化。必须先判断它们是否共享底层结构，是否存在耦合关系，是否适合理论证明、动态验证，或者二者同步。

---

## 3. 3.0.2：从描述结构到控制结构

3.0.1 说明局部指标之间高度耦合后，3.0.2 的思路自然上升到更高层：不再只看指标值，而是尝试描述和控制迷宫背后的结构对象。

这一阶段的两个关键概念是：

**Edge-Plan — Edge Plan — 边计划 / 结构边计划**
它表示先在抽象层面规划主路、死路、备选路、局部结构等关系。

**Decision Graph — Decision Graph — 决策图**
它表示从迷宫中提取真正影响选择的宏观结构，而不是直接相信每个格子的局部 degree。

这一步的思路转变是：

**3.0.1 控制的是指标结果，3.0.2 开始尝试控制结构原因。**

仅仅识别 Decision Graph 不够，因为识别只能回答“这个迷宫里有什么结构”，但数据工厂需要进一步回答“如何稳定生成这种结构”。因此 3.0.2 逐步走向：

**计划 → 注入 → 提取 → 对齐。**

也就是说，先计划一个结构，再把结构注入网格，再从生成结果中提取结构，最后比较计划结构和提取结构是否一致。

这个阶段暴露的核心问题是：计划结构、网格嵌入结构、验证器提取结构并不天然一致。计划里看似存在一条备选边，嵌入到网格后可能变成 shortcut；生成器认为某个结构已经成功注入，验证器却可能把它合并、压缩或忽略。

这里形成的工程经验是：

**当我们从描述目标结构走向生成目标结构时，必须同时定义结构的生成语义和验证语义。**

如果只定义“我想生成什么”，但没有定义“验证器如何承认它存在”，代码就可能生成“看起来像”的结构，而最终指标并不承认它。

这条经验后来直接影响 3.0.4 的 full extractor 思路：最终样本是否合格，不能由 generator 自证，而必须由独立验证器判定。

---

## 4. 3.0.3：严格构造的概念债务

3.0.2 暴露计划、注入、提取不一致后，3.0.3 尝试加强构造约束，让生成过程尽量保护计划结构。

这一阶段可以概括为：

**Plan-Preserving Generation — Plan-Preserving Generation — 计划保持生成。**

它的动机是合理的：如果宽松生成无法保证结构一致，就让构造过程更严格，让生成结果尽量保留预设结构。

但实践中，这条路线逐渐暴露出概念债务。

这里可以借用工程中的 Technical Debt — Technical Debt — 技术债务 概念。在 3.0.3 中，更准确地说是“概念债务”：为了让某个失败样本通过，需要增加一个新规则；为了修复这个新规则带来的副作用，又要增加另一个例外。这样系统逐渐从“生成样本”变成“维护一组复杂手写约束”。

这说明严格验证器和严格构造器不是同一个东西。

严格验证器可以告诉我们一个样本是否符合定义；但如果试图把验证器反向变成构造器，就可能让每个验证条件都变成一个构造约束，导致系统复杂度迅速膨胀。

3.0.3 的核心经验是：

**严格验证器可以保留，但不一定要反向写成严格构造器。**

当一个路线越来越依赖补丁、例外和局部规则时，上层应该暂停继续实现，转而寻找已有工程和理论经验，而不是继续把所有失败都修进构造器。

---

## 5. 从精确构造转向 QD-like archive

3.0.3 之后，关键思路转变来自一次方法论决策：当精确构造路线陷入细节后，不继续堆补丁，而是主动寻找已有工程、理论和论文中是否有类似问题的处理方式。

这里自然引入了：

**QD — Quality-Diversity — 质量多样性**
QD 类方法关注的不是寻找单个最优解，而是在一个行为或特征空间中找到多样且质量足够高的一组解。

**MAP-Elites — Multi-dimensional Archive of Phenotypic Elites — 表型精英多维档案**
MAP-Elites 是 QD 领域中的代表性方法。它用用户定义的行为特征或表型特征划分空间，并在每个区域保存表现较好的样本。

本项目并没有严格复刻原版 MAP-Elites。3.0.4 借鉴的是它的工程思想：

**不要求一个生成器精确构造所有目标，而是让候选池提供多样候选，再由统一验证器和目标 archive 选择样本。**

这一步是 3.0.n 的核心方法论转向。

从这里开始，问题不再是“如何精确构造每个目标迷宫”，而是：

1. 如何产生足够多样的候选；
2. 如何用同一套验证器解释候选；
3. 如何定义目标分布；
4. 如何让最终 archive 接近目标分布；
5. 如何通过 debug 报告判断缺口来自候选供给、验证器口径还是 archive 规则。

这条路线最终证明更适合当前阶段，因为它保留了强验证器，但不再要求生成器承担反向求解验证器的全部复杂度。

---

## 6. 3.0.4：候选池、验证器和目标档案

3.0.4 的大框架可以概括为：

**候选池 + full extractor + target archive。**

在这个框架里，职责被重新分离：

* generator / transform 负责产生候选；
* full extractor 负责解释样本结构；
* archive 负责根据目标分布接收样本；
* 工程壳负责记录、可视化、导出和审查。

这一步形成了一个非常重要的工程原则：

**生成器不能自己定义成功。**

样本是否属于某个目标桶，必须由独立验证器判断。这里可以使用工程中的 Single Source of Truth — Single Source of Truth — 单一事实来源 来描述：系统中涉及最终判断的关键事实，应当由一个可信来源给出，避免多个模块各自定义“成功”。

在 3.0.4 中，full extractor 就是最终分桶事实源。任何快速估算、近似判断或临时预筛，都不能静默替代 full extractor 进入最终 archive。

这条经验后来也暴露出代理协作问题：当任务中存在简化计算、近似判断或 fallback 路径时，下层代理必须主动上报其作用边界，不能让它静默影响最终结果。

## 7. 3.0.4 中期：缺桶必须看分层漏斗

3.0.4 中期，我们发现 accepted-only 统计不足以解释缺桶。

某个目标桶 accepted 少，可能有很多原因：

* 候选根本没有生成到；
* 样本没有通过 hard quality；
* 样本没有进入 full evaluated；
* 样本进入了 full evaluated，但被 duplicate / diversity / quota 拒绝；
* 目标桶本身与当前生成机制不匹配；
* 目标组合存在结构耦合，命中概率极低。

因此需要分层看：

```text
candidate
→ hard pass
→ full evaluated
→ accepted
```

这个分层漏斗是 3.0.4 的重要 debug 方法。

它改变了我们对“缺桶”的理解。缺桶不再被简单视为“生成器不行”，而是先判断缺口在哪一层。如果目标桶在 full_evaluated 层从未出现，说明候选供给不足；如果 full_evaluated 中有样本但 accepted 少，才进一步检查 archive、重复样本、quota 或质量门槛。

这一阶段还暴露出一个重要假设：我们曾默认已有 generator / transform 的组合概率足以覆盖目标，但没有先理论证明或动态验证这些组合概率。后来通过小规模动态验证发现，某些稀缺桶并没有稳定来自预期路径，甚至可能更多来自随机结构。这说明问题不是简单调度概率，而是候选供给机制本身没有针对目标结构。

这条经验应抽象为：

**当目标缺口来自候选空间供给不足时，调度器不能替代生成机制设计。**

---

## 8. 3.0.4 后期：目标分布来自真实手绘域

3.0.4 后期最重要的变化，是从“覆盖所有指标组合”转向“拟合真实手绘目标分布”。

通过手绘编辑器收集 handdraw maze 后，我们发现真实手绘分布并不是均匀覆盖所有指标桶，而是集中在少量结构区域。手绘迷宫通常更偏向：

* 更长的起点到终点路径；
* 更多真实决策点；
* 更多死胡同或端点结构；
* tree、single-loop、multi-loop 混合分布；
* 具有可玩性和设计感，而不是均匀随机覆盖。

这说明原先的完整桶空间更像是分析工具，不等于训练目标。

这里形成的经验是：

**指标笛卡尔积不是目标分布。真实目标域分布优先于想象中的全组合空间。**

因此 3.0.4 后期将目标区分为不同集合：

* 正式目标集合：来自手绘样本观察到的目标分布；
* 探索目标集合：用于发现新结构或扩展覆盖；
* 诊断目标集合：用于 debug 和理解失败；
* 暂不处理或结构受限集合：用于记录边界。

这不是 3.0.4 的局部技巧，而是目标分布工程中的通用经验。任何任务中只要存在多个样本集合、目标集合或评估范围，就必须先定义它们的语义，不能默认合并。

在 3.0.4 中，正式目标是覆盖 handdraw observed 分布；探索桶不应阻塞正式收官。这个修正最终让工程目标从“全桶焦虑”回到“手绘目标域覆盖”。

## 9. TDA-QD MazeForge：工程收敛而非单点技巧

3.0.4 最终收敛为 TDA-QD MazeForge。

**TDA-QD MazeForge — Terminal-Diameter Aligned Quality-Diversity MazeForge — 终端直径对齐的质量多样性迷宫工厂**

其中：

**TDA — Terminal-Diameter Alignment — 终端直径对齐**
它表达的是：任务端点必须绑定到结构复杂度。仅仅生成一个长结构不够，如果起点和终点落在很近的位置，任务仍然不是 long-path 任务。

**QD — Quality-Diversity — 质量多样性**
它表达的是：我们要生成一组接近目标分布、结构多样、质量合格的样本，而不是追求单个最优样本。

**MazeForge — 迷宫工厂**
它表达的是：系统已经从实验生成器变成数据工厂，必须具备生成、筛选、可视化、导出、验证和收官判断能力。

3.0.4 后期还有一些内部工程概念，例如 Pure TBI、CLO、RBR、Target-Class Route 等。正式工程经验中不需要展开它们的实现细节，只需要说明它们对应的抽象问题：

* 树类目标需要保持拓扑不变量的结构注入；
* 环类目标需要受控增加旁路，而不是随意 shortcut；
* 有潜力的中间样本需要可回滚的局部搜索；
* 稀缺目标需要更细粒度的目标路由，而不是粗粒度随机尝试。

这些内部概念是项目内工程工具，不应伪装成外部通用理论。

## 10. 3.0.4 的版本膨胀与责任归因

3.0.4 最终成功，但迭代版本较多。这不应该简单归因于“代码写得不好”或“算法想法不成熟”，而应分成几类。

第一类是必要动态探索。

例如，验证 full extractor 是否可信、handdraw 分布是否集中、候选池是否能覆盖目标、稀缺桶是否进入 full_evaluated 层。这些问题理论上很难一次证明，动态验证是合理路径。

第二类是算法假设失败。

例如，早期默认已有 generator / transform 组合能够覆盖稀缺桶，但动态验证发现候选供给不足。这类失败是有价值的，因为它排除了错误假设，并推动生成机制转向更有针对性的结构供给。

第三类是代理边界和任务拆解不足导致的返工。

例如，某些简化层或近似计算在边界未定义清楚时进入最终判断；某些新算法原语最初只是旧逻辑包装；某些工程输出最初只证明“运行成功”，没有证明“语义实现”。这些问题说明代码代理、算法代理、审查代理和上层决策代理的职责需要更清晰。

第四类是工程壳成熟过程。

例如 progress、blocking report、per-bin visualization、CSV、closure report、validate_quality 等。这些最初可能被视为附属功能，但后期证明它们是数据工厂不可缺少的审查系统。

这一阶段给出的代理协作经验是：

**高质量修改优先于快速完成。**

当任务涉及核心算法语义、结构生成、目标分布闭环、最终 archive、closure criterion 或数据集导出时，不能为了快速跑通而使用未声明的 wrapper、fallback、cheap estimate 或静默近似。如果任务过大，应主动拆分为算法定义、MVP、动态验证、正式实现、工程壳补全和最终审查。

## 11. 3.0.n 的核心工程经验

综合整个 3.0.n，可以提炼出以下经验。

### 11.1 可解性不是目标分布

可解样本只是训练数据的最低质量门槛。真正重要的是训练样本是否覆盖目标域结构。

### 11.2 描述坐标不等于控制坐标

一个指标能描述样本，不代表它能作为独立控制旋钮。多个指标共享底层结构时，必须先分析耦合关系。

### 11.3 结构对象必须同时有生成语义和验证语义

如果一个结构只在生成器中存在，而验证器无法识别，它就不能稳定服务数据工厂。

### 11.4 严格验证器不必反向变成严格构造器

验证器负责判断样本是否符合定义，不一定要把所有判断条件都反向写成构造规则。

### 11.5 外部工程经验应在路线补丁化时介入

当一个路线不断依赖补丁维持时，应暂停实现，查找已有工程、理论和论文经验。3.0.4 借鉴 QD / MAP-Elites 的 archive 思想，就是一次有效转向。

### 11.6 最终事实源必须统一

最终分桶、接受、收官判断必须由可信验证器提供事实。近似层、快速层、预筛层不能静默影响最终结论。

### 11.7 缺桶必须分层归因

accepted-only 不足以解释分布缺口。必须看 candidate、hard pass、full evaluated、accepted 各层。

### 11.8 目标域分布优先于指标笛卡尔积

完整指标组合空间可以作为分析工具，但不应默认成为训练目标。真实手绘分布才是当前阶段目标。

### 11.9 工程壳是数据工厂的一部分

可视化、CSV、报告、progress、blocking report、validate_quality、closure status 不是附属功能，而是判断样本能否进入训练和后续版本的必要证据。

### 11.10 算法假设失败可以接受，但必须能解释

某些问题理论证明复杂，动态验证更经济。关键不是避免失败，而是让失败能排除假设、支持转向，并沉淀为工程经验。

## 12. 对后续 1.0.9 / 2.0.9 样本替换测试的启发

当前 3.0.4 已经生成足够数量的样本，并且这些样本更接近手绘目标分布。因此下一步可以进入旧模块的数据替换测试，例如 1.0.9 和 2.0.9。

这里应保持一个原则：

**样本替换测试不是单纯换数据重新跑。**

它要回答：

1. 新分布是否提升手绘迷宫泛化；
2. 原模型是否只是过拟合旧生成器分布；
3. 旧 reward / planner / classifier 在新分布下暴露哪些新问题；
4. 新数据是否需要调整训练、验证和测试切分；
5. 如果模型失败，是模型能力不足、reward 语义不足，还是样本分布仍有缺口。

这意味着 3.0.4 的样本不是终点，而是后续模型能力诊断的新起点。

## 13. 未来方向

当前阶段暂时不继续扩展到更抽象、更高级的复杂迷宫，因为现有 3.0.4 样本已经足够支持下一步模型替换测试。短期重点应放在：

* 使用 3.0.4 样本替换旧训练集；
* 测试 1.0.9 / 2.0.9 等模块在新分布下的表现；
* 判断模型、reward、规划能力是否从新数据中受益；
* 继续通过 handdraw test 验证泛化能力。

更长期来看，如果项目进入更高阶段，样本分布发生大幅改变，例如：

* 迷宫从 8×8 扩展到更大尺度；
* 结构从规则网格扩展到更抽象拓扑；
* 任务从手绘迷宫迁移到更复杂的状态图；
* 迷宫分布需要模拟二进制程序中的 CFG — Control Flow Graph — 控制流图 或更复杂状态空间；
* 人工规则生成器难以覆盖目标域变化；
* 目标样本分布不再能通过少量 handdraw 样本和非 DL 数据工厂稳定描述；

此时可以考虑引入 DL — Deep Learning — 深度学习 进行样本生成或样本修复。

但这个方向不应过早启动。3.0.4 的经验说明，在目标分布、验证器、archive、debug 链路尚未稳定之前，直接使用 DL 生成器只会放大不可解释性。未来若使用 DL 生成样本，应建立在当前工程基础之上：

1. 已有目标分布；
2. 已有可信验证器；
3. 已有样本质量指标；
4. 已有 archive / quota / coverage 体系；
5. 已有可视化和审查报告；
6. 已能判断 DL 生成结果是否真正接近目标域。

因此，DL 样本生成不是替代 3.0.4 的非 DL 数据工厂，而是在数据分布复杂度显著上升后，建立在 3.0.4 经验之上的下一阶段扩展方向。

3.0.4 的阶段性结论是：

**在当前手绘迷宫分布下，非 DL 数据工厂已经足够；当未来目标分布大幅复杂化时，再考虑用 DL 扩展样本生成。**
